# Agent Guidelines

## Goal

This repository is a Kuzzle application template built in TypeScript and shipped as ESM.

## Runtime Rules

- Use ESM-compatible imports in source files.
- Always include the `.js` extension in internal imports (e.g. `import { MyApplication } from "./lib/MyApplication.js"`).
- **Do not add TypeScript path aliases.** There is no `imports` field in `package.json`, so `#alias/...` specifiers would compile but fail at runtime under plain `node`. Use relative imports.
- Keep the build output runnable with plain `node`.
- The active dev loop uses `tsx watch app.ts` — it runs the TypeScript sources directly and never touches `dist/`.

## Project Structure

- `app.ts` is the application entry point.
- `lib/` contains the application code.
  - `lib/MyApplication.ts` is the `Backend` subclass. **This is where a new module is wired**, by pushing it in `registerModules()`.
  - `lib/modules/<name>/` groups a module, a controller, a manager and its pipes (see `lib/modules/example/`).
  - A module extends `lib/modules/shared/Module.ts`: `register()` runs before Kuzzle starts (declare controllers, pipes and hooks), `init()` runs after (the SDK is usable).
  - `lib/utils/decorators/` provides `@ApiController` / `@ApiAction` / `@ApiRoute`, which declare the API surface.
- `tests/unit/` holds the vitest suites.
- `dist/` is generated by `tsc` and holds only `app.js` + `lib/` (tests are excluded from the build).
- `Dockerfile` builds a production image from the compiled output.
- `docker-compose.yml` runs the app in dev mode through `npm run dev`, alongside Redis and Elasticsearch.

## Commands

| Intent | Command |
| --- | --- |
| dev loop | `npm run dev` |
| build (authoritative) | `npm run build` → `tsc --build tsconfig.build.json` |
| type check (sources **and** tests) | `npm run test:types` |
| unit tests | `npm test` |
| lint | `npm run lint` |

## TypeScript Conventions

- Target Node ESM semantics (`module` and `moduleResolution` are both `NodeNext`).
- Two configs, on purpose:
  - `tsconfig.json` — the editor and `test:types` config; includes `app.ts`, `lib/`, `tests/` and `vitest.config.ts`.
  - `tsconfig.build.json` — extends it and narrows `include` to `app.ts` + `lib/`, so tests never land in the production image.
- Decorators require `experimentalDecorators` and `emitDecoratorMetadata`; leave them on.
- Avoid imports that only work in TypeScript but fail in emitted JavaScript.

## Lint Conventions

- `eslint-plugin-kuzzle` drives the whole config; `.eslintrc.json` only extends its presets.
- The toolchain is version-locked and the pin is deliberate: `eslint-plugin-kuzzle@0.0.15` peer-requires `eslint >= 8.50 <9` and `typescript >= 5.2 <5.5`. **Do not bump `typescript` past `5.4` without migrating the lint stack**, which means moving to the `eslint-9` dist-tag (`eslint-plugin-kuzzle@1.0.0-eslint-9.x`) and converting `.eslintrc.json` to a flat `eslint.config.js`.
- `new-cap` warnings on the decorator call sites are expected; only errors break the build.

## Docker Conventions

- Local compose should use `npm run dev` only.
- Production containers still start from the compiled application entry point (`node app.js`).
- The image build uses `npm ci` because `package-lock.json` is committed.
- `KUZZLE_ENV` (`local` | `main`) selects which `environments/<env>/kuzzlerc` is copied as `/var/app/.kuzzlerc`.

## Editing Rules

- Keep changes minimal and aligned with the existing template style.
- Update the README when the startup or build flow changes.
- Verify the build after touching module resolution, package metadata, or Docker startup commands.
- Update this file when the dev loop, Docker entrypoint, or module-resolution rules change.
